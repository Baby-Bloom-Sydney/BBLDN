## 2. CRITICAL

### C-1 — ✅ **CLOSED by FIX-1 (2026-09-16)** — `admin-on-behalf`'s levers are real, and the only gate is a value the caller supplies

|              |                                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity** | CRITICAL (latent — not live today)                                                                                                                                  |
| **File**     | `src/modules/admin-on-behalf/lib/admin-on-behalf-lever.ts:17` (`isAdmin`), `:19-49` (the eight levers); `src/modules/admin-on-behalf/admin-on-behalf.stub.ts:11-13` |
| **Owner**    | whichever unit writes `src/instrumentation.ts` (F-c today), jointly with the ADR-117 **Tier A** unit that builds the real inside                                    |

`adminOnBehalfLever()` is not a shell. It really calls `positions.advance`, `callLayer.chooseSlot` / `moveSlot` / `clearSlot` / `recordOutcome` / `openNannyCall` and `matching.autofire` — every one of which moves a real family's or nanny's stage. Its only gate is `actor.kind === 'admin'`, a check on a field the **caller hands in**, not a session-derived role, and there is no `mfaVerified` / `aal2` check at all (07 §5.4 row 2 requires both).

This is safe **today for one reason only**: nothing calls `configureAdminOnBehalf`, so the module-level binding sits on its fail-closed default and refuses everything. That is a structural guarantee, not a role-based one.

The trap is the shape of the seam. `configureAdminOnBehalf` accepts any `AdminOnBehalf`-shaped object with no compile-time signal that it must be wrapped in the auth gate first. A future integrator writing the boot file — under delivery pressure, reading "stub" as "harmless" — can write `configureAdminOnBehalf(stubAdminOnBehalf())` exactly as the swap test does, and that single line grants full on-behalf stage-advance, call-booking and autofire power to any caller who can shape an `Actor`. F-a flagged this in four places (module README, stub header, test header, PR body); it is loudly documented, which is why it is not a process failure — but a comment is not a gate.

Two further gaps compound it: `onBehalfOf` (the audit field 03 §2.5 and ADR-001 require on every admin move) is **optional on the `Actor` type and populated nowhere in the tree**; and `listAllowed` answers `[]` for a non-admin where every sibling lever answers `FORBIDDEN`.

**What must happen before anything calls `configureAdminOnBehalf`:** the real inside begins with `auth.requireRole('admin')` + `mfaVerified`; `onBehalfOf` becomes required and server-derived, never client-suppliable; and a gate exists — a test or a lint rule — that fails if `configureAdminOnBehalf` is reached with anything but that gated composition. Until then, **block any PR whose diff calls `configureAdminOnBehalf` without the gate visible in the same diff.**

**Checked, not assumed:** the boot file landed while this sweep was running (F-c, PR #11). `src/instrumentation.ts` on `modules-payments-160926-1` calls **`configureLog` and nothing else** — it deliberately wires no registry, for the same reason this finding gives, and says so in its own header. So the trap has not sprung. But note what actually held the line: two units independently choosing not to wire a seam, not a gate that would have stopped them.

The sweep did not fix this: the fix is an auth surface, which ADR-117 puts behind a security review, and it needs the Tier A ruling rather than a review agent's patch. What the sweep did add is `admin-on-behalf.fail-closed.test.ts`, which pins the unconfigured default that is currently the only thing holding the line.

## 3. HIGH

### H-1 — **FIXED** — the "every binding fails closed" claim was asserted by tests that could not fail

|              |                                                                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Severity** | HIGH                                                                                                                                                                                       |
| **Files**    | `areas` · `scoring` · `matching` · `call-layer` · `hire-docs` · `admin-on-behalf` `__tests__/*.swap.test.ts`; `positions` · `connections` · `placements` · `verification` (no case at all) |
| **Owner**    | REVIEW-1 — **fixed in this sweep**                                                                                                                                                         |

Both units close their PROGRESS entry with the same sentence: _"Every module-level binding **fails closed** until boot configures it."_ That claim is the entire safety argument for merging thirteen unreviewed connector modules to `main`. It turns out to be **true in the source and unevidenced in the tests**.

Six of the nine F-a modules have a test named "fails closed before boot configures …" which calls `configureX(...)` with a **hand-written object that returns the `x-not-configured` error**, then asserts that object returned it. It never reaches `x-registry.ts`. The `areas` test says so in its own comment: _"re-create the unconfigured state by installing a provider that mirrors it."_ A change that turned a real registry default from `err(...)` into `ok([])` would have passed every one of these tests.

Three more — `positions` (the aggregate root of the stage model), `connections` and `placements` — had no fail-closed case at all; their swap tests configure a stub in `beforeEach`, so the real default is never reached. `verification` — **Tier A, criminal-record checks** — had only folder-shape and allowed-imports assertions, so its refusal was entirely unexecuted.

F-b's `comms`, `scheduling` and `vetting-providers` are the exception and the model: they export their `unconfigured*` object from `index.ts` and install _that_, so their tests are genuine. The structural cause of the F-a gap is that F-a keeps its unconfigured object private inside the registry file, leaving no way to reach the real default from outside the module.

**Verified before fixing, not assumed:** I read all thirteen registries. Every one returns a coded `INTERNAL` error on every fallible method. The three documented exceptions (`areas.searchAreas` / `listAll` / `isInServiceArea`, `positions.listAllowed`, `adminOnBehalf.listAllowed`) have no `Result` in their contracts and answer the closed value — `[]` / `false` / no levers — never the open one. **The claim is true.** What was missing was the proof.

**Fix.** Ten new `*.fail-closed.test.ts` files, one per runtime module, each of which never calls `configure*` — vitest isolates module state per file, which is the only legal way to reach the factory default from outside a module without an import the boundary lint forbids. 23 new assertions. The approach was validated RED-first: flipping `areas-registry.ts`'s `lookupArea` to `ok(...)` turns the new test red, then the registry was restored. The tautological tests were left in place — deleting them is a change to F-a's own files beyond the minimum, and the new files supersede them; folding the two together belongs to the F-a follow-up unit.

### H-2 — **FIXED** — `stubCallLayer.listSlots` returns an empty success, unasserted and undocumented

|              |                                                                                               |
| ------------ | --------------------------------------------------------------------------------------------- |
| **Severity** | HIGH → closed as a documentation-of-intent gap                                                |
| **File**     | `src/modules/call-layer/call-layer.stub.ts:55`                                                |
| **Owner**    | REVIEW-1 — **pinned in this sweep**; the forward-to-`scheduling` decision stays with Phase 1g |

`listSlots: async () => ok(Object.freeze([]))` answers success with zero slots for any input, never asking `scheduling` for anything — while `openNannyCall`, five lines below in the same file, explicitly refuses with `E_PRECONDITION_FAILED` because _"the stub holds no calendar to book against."_ The README documents the refusal and says nothing about the empty list, and the swap test never called `listSlots` at all.

05 §3 rule 6 is the standard here: a stub whose success is indistinguishable from real work is acceptable **only** where a swap test asserts that behaviour deliberately. It did not.

On the merits the behaviour is defensible and was left alone: "no slots free" is a real answer from an empty in-memory calendar, whereas "booked" is not an answer a calendar-less stub can give — so the asymmetry with `openNannyCall` is correct, not a bug. Changing it to refuse would be a contract decision (03 §2.7 does not settle it) and is not a review agent's to make. **Fix:** a swap-test case pinning the emptiness as a decision on the record, so wiring `listSlots` through to `scheduling` later has to change the test on purpose.

## 6. What the sweep confirmed rather than found

Recorded because a later reader should not have to re-derive it.

- **The Tier A shells are genuinely inert.** `verification`, `vetting-providers` and `admin-verification` terminate every exported path in a coded refusal — and `admin-verification` exports no callable value at all, only types.
